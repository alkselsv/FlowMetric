# Эксперименты: обнаружение × сопровождение × повторная идентификация × GPT-6 Astra

Клип: `data/hf_*.mp4` — 15 с, 361 кадр, 1920×1080, 24 fps, 30 человек. Эталон: `benchmark/ground_truth.json` с якорями голов на кадрах 0 и 86, пятью сотрудниками, девятью событиями и интервалами состояний.

Этот отчёт описывает экспериментальную сетку и контрольные прогоны основной
команды. Он предназначен не только для выбора максимального F1, но и для
понимания компромиссов между полнотой обнаружения, непрерывностью личности,
правильностью ролей, событиями, состояниями и временем обработки.

> Основные колонки непрерывности (`continuity`) и ролей считаются по всей
> цепочке для всех эталонных людей. Метрики сопоставленного подмножества
> (`mapped`) характеризуют только людей, связанных с якорями, и приведены
> отдельно.

## Как читать этот отчёт

- **Конфигурация** — сочетание детектора, алгоритма сопровождения и, при
  наличии, локальной модели повторной идентификации.
- **Локальный режим** использует только детектор и трекер.
- **Гибридный режим** дополняет локальные траектории сохранённым ответом Astra.
- **Основной конвейер** использует галереи пронумерованных фрагментов
  траекторий. Экспериментальная сетка использует отдельные сохранённые
  полнокадровые ответы зрительно-языковой модели; эти результаты нельзя
  напрямую считать повтором основной команды.
- Высокая F1 событий при низком покрытии людей может быть следствием того, что
  система оценивается на небольшом числе событий. Поэтому таблицы нужно читать
  вместе с покрытием, непрерывностью и числом итоговых идентификаторов.
- Все результаты относятся к одному проверочному клипу. Различия, равные одному
  событию, не доказывают преимущество на новых камерах.

## Объём и артефакты

- 222 конфигурации «детектор + трекер», включая 84 конфигурации с трекерами BoxMOT 25.
- Девять режимов на конфигурацию: локальный и восемь сохранённых ответов
  зрительно-языковых моделей. Всего 1998 строк.
- Гибридные колонки в `experiments_summary.csv` — среднее только по трём
  повторам Astra 1 кадр/с с уровнем рассуждения `low`; запуск `medium` в это
  среднее не входит.
- Карта столов отдельно оценена при `TABLE_GAP` 0.2, 0.35 и 0.5.

### Состав сетки

Детекторы включают YOLO11s при размерах 640 и 1280, YOLO11m/x, YOLO26s/m и
RF-DETR Small/Medium/Large, в том числе варианты RF-DETR с разрешением 1024 и
калиброванной шкалой уверенности. Калиброванный вариант повторно использует
боксы базового детектора и меняет только оценку уверенности.

Трекеры BoxMOT 12 включают ByteTrack, OC-SORT, BoT-SORT без ReID и с OSNet или
CLIP-ReID, Deep OC-SORT, StrongSORT и BoostTrack++. Отдельный контур BoxMOT 25
оценивает OccluBoost, BoT-SORT, Hybrid-SORT, BoostTrack, ByteTrack, OC-SORT и
SFSORT на штатных и общих заданных порогах. Для YOLO дополнительно оцениваются
варианты BoT-SORT из Ultralytics.

Не каждое сочетание применимо ко всем детекторам, поэтому итоговое число равно
222, а не простому произведению количества моделей и трекеров.

Актуальные машинно-читаемые результаты:

- [`experiments.csv`](experiments.csv) — каждый прогон;
- [`experiments_summary.csv`](experiments_summary.csv) — одна строка на конфигурацию;
- [`experiments_tables.md`](experiments_tables.md) — полная ранжированная таблица;
- `experiments*_tablegap{0.2,0.35,0.5}.csv` и соответствующие Markdown-таблицы — варианты со столами.

Основная команда использует профиль BoT-SORT с повышенной полнотой и галерею
фрагментов траекторий Astra. Контрольный прогон имеет покрытие якорей `30/30`,
55 итоговых ID, непрерывность `0.855`, точность ролей `0.933`, строгую/нестрогую
F1 `0.667/0.889` и временной IoU ожидания/потребления `0.748/0.746`. CSV выше
описывают отдельную зафиксированную сетку с полнокадровыми ответами модели; её
значения не смешиваются с галерейным прогоном.

### Уровни данных в отчётах

`experiments.csv` хранит одну строку на конкретный запуск. В ней есть имя
детектора, трекера и ReID, задержки, режим Astra, количество итоговых ID,
покрытие, непрерывность, роли, TP/FP/FN, F1 и временной IoU состояний.

`experiments_summary.csv` группирует строки по конфигурации детектора и
трекера. Локальные колонки относятся к одному детерминированному прогону,
гибридные — к среднему трёх одинаково настроенных Astra-повторов `low`.
`hybrid_runs=3` показывает число повторов, вошедших в среднее.

Markdown-файлы `experiments_tables*.md` формируются из соответствующих CSV и
нужны для чтения человеком. Источником чисел считаются CSV, а не вручную
переписанная таблица в этом отчёте.

Основные группы колонок `experiments.csv`:

| Колонки | Содержимое |
|---|---|
| `detector`, `det_key`, `det_ms` | человекочитаемое имя, устойчивый ключ и задержка детектора |
| `tracker`, `trk_key`, `reid`, `trk_ms` | алгоритм сопровождения, его ключ, модель ReID и задержка |
| `mode`, `astra_calls`, `astra_frames` | режим оценки и объём обращений к Astra |
| `local_tracks`, `pred_ids`, `astra_verified` | число локальных фрагментов, итоговых ID и подтверждённых Astra личностей |
| `anchored`, `anchor_coverage` | число и доля сопоставленных эталонных людей |
| `continuity*`, `role_acc*` | непрерывность идентификаторов и точность ролей |
| `strict_*`, `loose_f1`, `mae_s` | события, TP/FP/FN и средняя абсолютная ошибка времени |
| `waiting_tiou`, `consuming_tiou` | временной IoU состояний клиентов |

Ключи `det_key` и `trk_key` следует использовать в скриптах вместо подписей:
подписи могут становиться подробнее, а ключи предназначены для устойчивого
сопоставления строк.

## Метрики

| Метрика | Определение |
|---|---|
| Полнота якорей | Доля эталонных голов, найденных детектором на двух опорных кадрах при уверенности ≥ 0.3 |
| Покрытие якорей | Доля из 30 эталонных людей, которым удалось назначить предсказанный ID |
| Общая непрерывность | Средняя доля ожидаемого присутствия всех эталонных людей, покрытая их главным ID; несопоставленный человек получает 0 |
| Непрерывность сопоставленных | Та же величина только на сопоставленном подмножестве; читать вместе с покрытием якорей |
| Роли общие / сопоставленные | Точность staff/customer по всем 30 людям / только по сопоставленным людям |
| Строгая F1 | Совпали тип события, участники после сопоставления ID и время ±1 с |
| Нестрогая F1 | Совпали тип и время ±1 с, участники не проверяются |
| tIoU ожидания/потребления | IoU объединений временных интервалов; пересечения не учитываются дважды, интервалы несопоставленных ID входят в ложноположительную часть объединения |

Колонки `continuity`, `continuity_staff` и `role_acc` в CSV описывают общую
оценку всей цепочки. Значения для сопоставленного подмножества записаны явно
как `continuity_mapped` и `role_acc_mapped`.

Точность событий вычисляется как `TP / (TP + FP)`, полнота — как
`TP / (TP + FN)`, а F1 — как гармоническое среднее точности и полноты. Если
предсказаний нет, соответствующие крайние случаи обрабатываются кодом
`metrics.py`, поэтому для точного повторения нужно использовать сам оценщик, а
не пересчитывать отдельные строки вручную.

Временной IoU равен `intersection / union`, где сначала объединяются
перекрывающиеся интервалы одного типа. Поэтому значение находится в диапазоне
от 0 до 1 и не увеличивается из-за двойного учёта перекрытий.

### Правила оценки и обработки

- tIoU вычисляется по объединениям интервалов и всегда находится в диапазоне `[0, 1]`.
- Эталонные ID могут быть произвольными и разреженными; несопоставленные люди
  снижают непрерывность и точность ролей.
- Обслуживание извлекает конечный автомат «приближение → взаимодействие →
  удаление». Кроме случая с ненаблюдаемой левой границей на первом кадре,
  требуется движение к клиенту именно сотрудника, подтверждённая остановка,
  минимальная длительность, покрытие и достаточная доля неподвижных наблюдений.
  Один сотрудник связан не более чем с одним клиентом, а один клиент — не более
  чем с одним сотрудником.
- Захват использует узкую зону 0.9 высоты прямоугольника сотрудника. Конец
  подтверждается минимум 0.3 с движения и ростом расстояния либо выходом из
  узкой зоны. Расширенная зона 1.1 даёт дополнительное свидетельство ухода и
  управляет повторным срабатыванием пары. Разрывы до 0.5 с считаются дрожанием
  траектории и объединяются с тем же эпизодом. После завершения блокируется
  только конкретная пара до выхода из расширенной зоны или 1.5 с отсутствия.
- Подтверждённый эпизод записывается в `service_intervals` с эвристической
  уверенностью и признаками ненаблюдаемых границ. Интервал с неизвестным началом
  не публикует точечных событий; интервал с неизвестным концом публикует
  наблюдаемый `service_start`, но не `service_end`.
- Дополнительная проверка обслуживания использует диапазоны уверенности
  `<0.3 / 0.3–0.8 / >0.8`: низкие кандидаты отклоняются локально, высокие
  принимаются локально, неоднозначные проверяются выбранной реализацией. Astra
  получает 4–8 размеченных фрагментов кадров и возвращает только `is_service`,
  назначенные ID и уверенность. Локальная реализация извлекает признаки рук,
  корпуса, наклона, предметов и длительности контакта на последовательности до
  48 кадров, затем применяет JSON-MLP. Обе реализации сохраняют исходные ID и
  границы.
- Клиент, появившийся в середине видео, становится доступен для обслуживания
  только после наблюдаемой посадки; `leave_kitchen` создаётся только для
  сотрудника; для `exit` требуется плотный непрерывный конечный участок
  траектории.
- Основной ReID получает только пронумерованные галереи фрагментов траекторий.
  Объединение требует взвешенную уверенность и минимум два подтверждающих
  фрагмента; остальные решения сохраняются как `abstain`. Структура
  непересекающихся множеств запрещает объединять разные Astra-ID одного пакета
  и локальные траектории, одновременно видимые как разные люди. Сохранённые
  полнокадровые артефакты экспериментальной сетки используют венгерский
  алгоритм с предварительным порогом IoU и теми же жёсткими ограничениями.
- Ожидание и потребление ведутся отдельным конечным автоматом клиента. Ожидание
  использует посадку и сигнал доставки или активности; потребление определяется
  начальной устойчивой занятостью либо микродвижением верхней части тела и не
  выводится из наличия точечного события обслуживания.

### Контракт автомата обслуживания с приоритетом точности

Обычный кандидат появляется только при наблюдаемом приближении сотрудника: в
окне 1.5 с он должен двигаться и сократить нормированное расстояние, а финальная
проверка требует уменьшения расстояния минимум на 0.18 высоты его прямоугольника.
Кандидат первого кадра с ненаблюдаемой левой границей — явно помеченное
исключение. После входа в узкую зону 0.9 пара захватывается при остановке на
0.4 с. Подтверждённый интервал должен длиться минимум 1 с, иметь не менее трёх
наблюдений, покрытие не ниже 0.5 и долю неподвижных наблюдений не ниже 0.72. При
включённой карте столов дополнительно действуют узкий и расширенный пороги
`0.35/0.55`.

`events` и `service_intervals` намеренно имеют разную семантику. Взаимодействие,
уже идущее на первом кадре, присутствует только в `service_intervals`: его
неизвестное начало не порождает `service_start` или `service_end`, поэтому
метрики точечных событий его не учитывают. Взаимодействие с наблюдаемым началом
и неизвестным концом публикует `service_start` с `right_censored=true`, но не
публикует `service_end`. Поле `confidence` — эвристическая оценка, а не
калиброванная вероятность.

Пороговые значения специфичны для этого 15-секундного проверочного клипа. На
нём они разделяют два истинных обслуживания и сложные отрицательные примеры.
Перед промышленным применением нужна оценка на отложенных видео и других
камерах.

Среднее по большому числу конфигураций отвечает на вопрос об общей тенденции,
а не о лучшей рабочей точке. Некоторые конфигурации используют слабые
детекторы или неподходящие пороги и снижают среднее. Для выбора практического
режима следует отдельно смотреть верхние строки, задержку и переносимость.

### Практический выбор

- Основной `track.py` использует ultralytics BoT-SORT. С Astra 1 кадр/с `low`
  он в среднем даёт 41.7 ID, покрытие 28/30, непрерывность
  `0.857 / 0.918` общую/сопоставленную, роли `0.933 / 1.000` и строгую F1
  `0.889` при точности и полноте `0.889`.
- BoxMOT 12 BoT-SORT без ReID даёт 34.0 ID и меньшую общую полноту: покрытие
  26/30, непрерывность `0.804 / 0.928`, строгую F1 `0.824`.
- BoxMOT 25 BoostTrack с заданными порогами лидирует в сетке и доступен через
  экспериментальный запуск. Его строгая F1 на этом клипе равна `0.941`;
  переносимость требует проверки на других камерах.
- Для режима без Astra Hybrid-SORT BoxMOT 25 даёт в среднем по шести
  детекторам локальную F1 `0.419` на штатных порогах и `0.428` на заданных; с
  Astra значения составляют `0.422` и `0.456`.

## Детекторы, трекеры и ReID

Среди трекеров без BoxMOT 25 лучший детектор — YOLO11s 1280: средняя
гибридная F1 `0.804` и общая непрерывность `0.831`. Для сравнения, YOLO11s 640
даёт `0.325` и `0.495`; более крупные модели при разрешении 1280 не дают
стабильного выигрыша по сравнению с YOLO11s.

Внешние ReID-модели у BoT-SORT не окупают задержку. В среднем по 14 детекторам:

| BoT-SORT | Задержка сопровождения, мс | Локальная непрерывность | Гибридная непрерывность | Локальная / гибридная F1 |
|---|---:|---:|---:|---:|
| Без ReID | 1.4 | 0.473 | 0.612 | 0.306 / 0.391 |
| OSNet x0.25 | 24.6 | 0.473 | 0.619 | 0.287 / 0.418 |
| OSNet x1.0 | 65.3 | 0.470 | 0.617 | 0.287 / 0.409 |
| CLIP-ReID | 220.8 | 0.463 | 0.611 | 0.268 / 0.390 |

Задержка в таблице показана для YOLO11s 1280, а показатели качества усреднены по всем 14 детекторам. Небольшие различия качества на единственном клипе меньше экспериментальной неопределённости.

Задержки разных семейств нельзя считать полностью сопоставимыми. BoxMOT
получает заранее сохранённый поток обнаружений, а Ultralytics выполняет
`model.track`, который включает детекцию и сопровождение; в отчёте из этого
времени вычитается отдельно измеренное время детектора. Разные прогревы и
синхронизация устройства также влияют на миллисекунды. Для производительного
сравнения нужны несколько повторов, медиана, 95-й процентиль и единый входной
поток обнаружений.

Перед первым кадром BoxMOT получает три повторных кадра прогрева. Это позволяет
трекерам с подтверждением через несколько наблюдений выдать ID на кадре 0, где
находится эталонный якорь. Такой прогрев имитирует уже работающий видеопоток, но
его следует учитывать при переносе результатов на запуск с самого начала
записи.

RF-DETR без дообучения хуже распознаёт дальних людей и использует другую шкалу
уверенности. Калибровка и разрешение 1024 повышают его показатели, а лучший
баланс качества и скорости в этой сетке даёт YOLO11s 1280. Полные значения по
каждому детектору находятся в [`experiments_tables.md`](experiments_tables.md).

## Карта столов

`tables.py` агрегирует COCO-детекции столов по видео, а `scene.py` проверяет разрешение и геометрию карты. В основном CLI карта включается явно:

```bash
python track.py --tables config/tables.json
```

С картой клиент должен иметь домашний стол, а сотрудник — находиться рядом с этим столом. Карта не включается по умолчанию, потому что влияние порога зависит от сцены.

Средняя разница между режимом с картой столов и теми же 222 конфигурациями без неё:

| TABLE_GAP | ΔF1 локально | ΔF1 гибридно | Δточности / Δполноты гибридно | ΔtIoU ожидания | F1 основной конфигурации | Лучший F1 |
|---:|---:|---:|---:|---:|---:|---:|
| 0.2 | −0.003 | **−0.083** | −0.052 / −0.115 | −0.113 | 0.750 | 0.800 |
| 0.35 | −0.008 | **−0.009** | −0.026 / +0.014 | −0.034 | **0.889** | **0.941** |
| 0.5 | −0.010 | −0.018 | −0.033 / +0.002 | −0.008 | **0.889** | **0.941** |

При 0.35 гибридная F1 выше у 13.1% конфигураций, ниже у 42.3% и одинакова у
44.6%; F1 основной конфигурации равна `0.889` как с картой, так и без неё.
Порог 0.2 слишком строг и снижает полноту, а 0.5 сохраняет основную F1, но даёт
небольшое среднее снижение. Максимальная F1 с картой и без неё равна `0.941`,
поэтому карта служит дополнительным сигналом конкретной сцены, а не
универсальной настройкой.

При 0.35 и 0.5 лучший результат даёт YOLO11s 1280 + BoostTrack BoxMOT 25 с
заданными порогами: F1 `0.941`, общая непрерывность `0.852`. При 0.2 эта
конфигурация также занимает первое место с F1 `0.800`.

## Надёжность конвейера

- Конфигурации камеры и столов привязаны к разрешению; несовпадение останавливает запуск до детекции и API-вызовов.
- Основной кэш Astra содержит версию, SHA-256 и размер видео, параметры видео и
  выбора кадров, модель и уровень рассуждения, версии галереи, запроса, схемы и
  координатные метаданные. Кэш с несовпадающим манифестом или без обязательных
  полей отклоняется. При наличии API-ключа конвейер получает новый ответ и
  атомарно записывает совместимый кэш.
- Astra-проверка обслуживания использует отдельный атомарный кэш, привязанный к
  видео, траекториям, кандидатам, фрагментам кадров, столам, модели, версии
  запроса, схеме и порогам маршрутизации. Кэш ReID для неё не применяется.
- Полностью локальная проверка не отправляет кадры во внешний API. Её JSON-MLP
  имеет строгую версию и схему признаков; признаки позы, предметов и вероятность
  сохраняются в аудите кандидата. Начальный файл весов требует замены на модель,
  обученную по размеченным эпизодам.
- Галерейные ответы Astra проверяются как точное разбиение известных
  идентификаторов фрагментов на группы личности и отказы от решения, включая
  роли, уверенность, число подтверждений и отсутствие дополнительных полей.
  Полнокадровые ответы экспериментального контура проверяются по ID, ролям,
  кадрам, координатам, размерам и покрытию пакетов.
- Экспериментальные кэши жёстко привязаны к имени эталонного видео; запуск
  отказывается применять их к другому источнику.
- `--stages eval` не декодирует всё видео в память, если нужны только сохранённые детекции/треки и пересчёт метрик.

## Ограничения

- Один клип, 30 человек и 9 событий. Разницу меньше примерно `0.1` F1 нельзя
  считать убедительной без новых видео.
- Правила зон и событий специфичны для этой камеры, поэтому возможна подгонка.
- Якоря есть только на двух кадрах. Метрики сопоставленного подмножества условны,
  а общие метрики смешивают ошибки детектора, сопоставления якорей и
  сопровождения — это отражает качество всей системы.
- Сравнение трекеров использует один набор зафиксированных ответов
  зрительно-языковой модели. Оценка вариативности API ограничена тремя
  повторами `low`.
- Карта столов основана на автоматической детекции и содержит геометрические неточности; для реальной установки лучше ручная калибровка.
- Показатели скорости относятся к Apple Silicon (MPS), FP32, размеру пакета 1,
  без TensorRT/FP16.
- Качество Astra- и локальной проверки обслуживания не входит в CSV. Для Astra
  нет зафиксированной полной сетки ответов, а начальный локальный MLP использует
  ручную инициализацию на текущем проверочном клипе и не обучен на независимом
  наборе. Любое бинарное отклонение может уменьшить число ложных событий либо
  удалить истинный эпизод, поэтому нужна отдельная оценка на отложенных данных.

## Что можно и нельзя заключить из результатов

Можно заключить, что на данном клипе Astra 1 кадр/с обычно уменьшает
фрагментацию идентификаторов и повышает непрерывность по сравнению с локальным
режимом. Можно также воспроизводимо сравнивать конфигурации внутри одной
экспериментальной схемы.

Нельзя утверждать, что конфигурация с максимальной F1 будет лучшей на другой
камере. Нельзя интерпретировать разницу одного события как статистически
устойчивое преимущество. Нельзя сравнивать задержки разных аппаратных платформ
без повторного измерения. Нельзя смешивать результаты галерейного основного
конвейера и полнокадровой экспериментальной сетки как один и тот же протокол.

## Воспроизведение

Полная сетка значительно тяжелее основного запуска: она использует несколько
детекторов, трекеров, веса ReID и сохранённые ответы моделей. Для первого
знакомства с проектом достаточно основного `requirements.txt` и команды из
корневого README.

```bash
# Базовые зависимости обязательны.
pip install -r requirements.txt

# Дополнительные библиотеки экспериментальной сетки.
pip install -r requirements-experiments.txt
pip install --no-deps boxmot==12.0.2

# Сформировать ответы зрительно-языковой модели; нужен API-ключ.
python experiments/astra_variants.py

# Полная сетка: обнаружение, сопровождение и оценка.
python experiments/run_experiments.py

# Только оценка сохранённых артефактов; API-вызовы не выполняются.
python experiments/run_experiments.py --stages eval

# Оценка с картой столов
python tables.py
python experiments/run_experiments.py --stages eval --table-gap 0.35

# Модульные тесты.
.venv/bin/python -m unittest discover -s tests -v
```

Этапы экспериментального запуска разделены, чтобы дорогие обнаружения и
траектории можно было использовать повторно. Кэши детекций и треков находятся
в `data/experiments/`, а итоговые таблицы — в `reports/`. Частичный запуск не
следует принимать за полный отчёт: проверяйте число строк и поле
`hybrid_runs`.

BoxMOT 25 запускается из отдельной рабочей копии через
`experiments/boxmot25_tracks.py` и не входит в зависимости основной команды
`track.py`. Версия этой рабочей копии влияет на воспроизводимость, поэтому при
переносе эксперимента на другую машину следует фиксировать точный коммит.
