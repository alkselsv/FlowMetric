# Эталонная проверка для клипа `data/hf_*.mp4`

Источник исходной разметки: [nofriendsatall/video_analytics](https://github.com/nofriendsatall/video_analytics).

Этот каталог содержит небольшую эталонную разметку, с которой сравнивается
результат FlowMetric. Эталон нужен для воспроизводимого ответа на три разных
вопроса:

1. нашёл ли детектор всех людей на опорных кадрах;
2. сохранил ли трекер одну личность на протяжении ожидаемого времени;
3. правильно ли определены роли, события и длительные состояния клиентов.

Клип короткий и используется как проверочный набор для разработки. Его нельзя
считать независимой оценкой качества на других камерах.

| Файл | Что это |
|---|---|
| `Timings.txt` | Сотрудники, события с временными отметками и интервалы потребления |
| `First.png`, `Second.png` | Кадры 0 и 86 с номерами людей над головами |
| `ground_truth.json` | Якоря голов в координатах 1920×1080, роли, события и состояния |

Основные разделы `ground_truth.json`:

| Раздел | Содержимое |
|---|---|
| `staff` | список идентификаторов сотрудников; остальные якорные ID считаются посетителями |
| `anchors` | точки головы на кадрах 0 и 86 для сопоставления ID |
| `events` | тип события, время и участники |
| `states` | интервалы ожидания и потребления заказа |

Координаты относятся к исходному разрешению 1920×1080. Если видео
масштабируется или заменяется, якоря нельзя переносить без пересчёта.

Запуск оценки:

```bash
python metrics.py \
  --tracks data/output/tracks.json \
  --events data/output/events.json \
  --gt benchmark/ground_truth.json
```

Команда не запускает детектор и не обращается к Astra. Она читает уже созданные
`tracks.json` и `events.json`. Для полного запуска с обработкой видео и
последующей оценкой используйте:

```bash
python track.py \
  --source data/hf_20260519_173215_0e502bf6-374c-4039-ab2e-fded1fdf5558.mp4 \
  --out data/output/benchmark/tracked.mp4 \
  --camera config/camera.json \
  --tables config/tables.json \
  --gt benchmark/ground_truth.json \
  --device auto \
  --no-astra
```

## Как выполняется сопоставление людей

В `ground_truth.json` для каждого человека указаны координаты головы на кадре 0,
кадре 86 либо на обоих. Оценщик ищет предсказанный прямоугольник, содержащий
этот якорь, и назначает эталонному человеку итоговый идентификатор траектории.
Один предсказанный идентификатор не должен одновременно объяснять двух разных
эталонных людей.

Якорь — это только способ установить соответствие идентификаторов. Он не
является покадровой разметкой траектории, поэтому непрерывность в этом наборе —
приближённая оценка. Переключение идентификатора между опорными кадрами может
быть замечено лишь косвенно по покрытию ожидаемого присутствия.

`metrics.py` сначала связывает GT-людей с предсказанными ID по якорям на кадрах 0 и 86, затем считает:

- `continuity_mean` — общую непрерывность: долю ожидаемого присутствия всех
  эталонных людей, покрытую их главным идентификатором; несопоставленный человек
  получает ноль;
- `continuity_mapped` — непрерывность только для сопоставленных людей; её нужно
  читать вместе с покрытием (`coverage`);
- общую точность ролей и условную точность ролей только на сопоставленном
  подмножестве;
- строгие события: совпали тип, участники и время с допуском ±1 с;
- нестрогие события: совпали только тип и время;
- временной IoU (`tIoU`) ожидания и потребления как отношение длительности
  пересечения интервалов к длительности их объединения. Перекрытия внутри
  одного набора учитываются один раз, а состояния несопоставленных
  предсказанных людей увеличивают ложноположительную длительность.

Основными для интерпретации служат общие метрики всей цепочки. Значения на
сопоставленном подмножестве показывают качество системы после успешного
обнаружения человека и поэтому могут выглядеть заметно лучше.

### Расширенные метрики ReID

Раздел `reid` в `benchmark_report.json` поддерживает два явно разделённых
протокола. Если ground truth содержит покадровый объект `trajectories` вида
`person_id: {frames: [...], boxes: [[x1,y1,x2,y2], ...]}`, оценщик считает
IDF1, HOTA по IoU-порогам 0.05–0.95, ложные объединения разных GT-людей,
fragmentation и ID switches по каждому человеку. Дополнительно публикуются
срез сотрудников и статистика предсказанных ID короче 0.5 секунды.

Текущий `ground_truth.json` содержит только одиночные identity anchors, поэтому
стандартные `idf1` и `hota` записываются как `null`. Вместо них раздел `proxy`
показывает приближённые IDTP/IDFP/IDFN, IDF1 и HOTA на основе ожидаемых
интервалов присутствия. Ложные объединения и переключения в этом режиме имеют
явный scope `reference_frames_only`/`between_reference_frames_only`; их нельзя
интерпретировать как покадровые tracking-метрики. Поле
`source_tracklets_in_primary_id` показывает, сколько локальных фрагментов было
успешно собрано в основной ID привязанного человека.

### Пример чтения метрик

Если покрытие равно `26/30`, непрерывность на сопоставленных людях равна
`0.93`, а общая непрерывность — `0.80`, это означает: уже найденные люди
сопровождаются хорошо, но четыре пропущенных человека снижают качество всей
системы. Если нестрогая F1 событий равна `0.89`, а строгая — `0.67`, времена и
типы событий в основном верны, но часть событий связана с неверными
идентификаторами участников.

## Галерея фрагментов траекторий и решения ReID

Основной гибридный конвейер передаёт Astra только изображения с сеткой миниатюр
(«контактные листы»). Они состоят из локальных фрагментов кадров, подписанных
идентификатором траектории и номером кадра. Ответ содержит группы существующих
идентификаторов, роль, уверенность и `abstained_tracklet_ids`; координаты в
контракт не входят. Для локального объединения нужны минимум два
подтверждающих фрагмента и достаточная взвешенная уверенность. Решение
сохраняется как `merge`, `reject` или `abstain`.
Пространственно разные траектории, одновременно видимые в кадре, образуют
жёсткий запрет на объединение.

Профиль повышенной полноты `config/botsort_recall.yaml` использует пониженные
пороги и увеличенное время хранения траектории для малых или частично
перекрытых людей. На проверочном клипе покрытие якорей основной команды равно
`30/30`. Галерейный прогон даёт 55 итоговых идентификаторов, непрерывность
`0.855`, временной IoU ожидания `0.748`, потребления `0.746`, строгую F1 `0.667`
и нестрогую F1 `0.889`. Короткое наблюдение сотрудника остаётся в состоянии
отказа от решения, поэтому у одного события правильны тип и время, но не
строгий идентификатор участника.

## Конечный автомат состояний клиента

Ожидание (`waiting`) и потребление заказа (`consuming`) ведутся как два
независимо проверяемых состояния. Ожидание использует посадку или начальную
занятость стола и завершается по подтверждённой доставке либо активности
клиента. Потребление не выводится из наличия точечного события обслуживания:
сигналом служит стабильная занятость стола на границе клипа или локальная
активность верхней части тела при неподвижных ногах. Уверенность и основание
решения записываются в `states`, а входные признаки — в
`customer_state_audit`.

## Контракт конечного автомата обслуживания

Обслуживание определяется FSM. Для обычного кандидата требуется наблюдаемое
приближение именно сотрудника в течение окна 1.5 с, вход в зону не дальше 0.9
высоты его бокса, остановка для захвата пары и достаточная доля стационарных
наблюдений (`0.72`) на всём подтверждаемом интервале. Финальная проверка
приближения требует уменьшения расстояния не менее чем на 0.18 высоты бокса.
Кандидат первого кадра с ненаблюдаемой левой границей — явно помеченное
исключение, для которого приближение не наблюдается. Один сотрудник может
одновременно обслуживать не более одного клиента, а один клиент не может быть
связан сразу с двумя сотрудниками.

Завершение подтверждается минимум 0.3 с движения сотрудника и ростом расстояния
либо выходом из узкой зоны. Расширенная зона 1.1 используется как дополнительное
свидетельство ухода и как гистерезис повторного срабатывания пары. Разрывы до
0.5 с считаются дрожанием траектории и объединяются с тем же эпизодом. Во время
паузы повторного срабатывания блокируется только конкретная пара
сотрудник–клиент. Пара снова доступна при выходе из расширенной зоны либо при
отсутствии наблюдений в течение 1.5 с; другие сочетания сотрудников и клиентов
остаются доступными.

`events.json` содержит два представления:

- `events` — наблюдаемые точечные `service_start/service_end`, по которым
  считаются строгие и нестрогие метрики событий;
- `service_intervals` — полные эпизоды с `left_censored`, `right_censored` и
  эвристической уверенностью `confidence`. Это значение полезно для
  ранжирования, но не является калиброванной вероятностью.

Контракт отдаёт приоритет точности. Если взаимодействие уже шло на первом
кадре, его начало неизвестно: интервал с ненаблюдаемой левой границей остаётся
только в `service_intervals` и не публикует точечных событий. Если взаимодействие
началось в кадре, но не закончилось до конца наблюдения, интервал с
ненаблюдаемой правой границей публикует наблюдаемый `service_start` с флагом
`right_censored`, но не `service_end`.

Все численные пороги конечного автомата специфичны для этого проверочного
клипа. Для универсальных значений нужна оценка на отложенных видео, других
камерах и плотностях посетителей.

## Проверка кандидатов обслуживания через Astra

Опция `--service-verifier astra` включает маршрутизацию по уверенности конечного
автомата: значения ниже `0.3` отклоняются локально, диапазон `0.3–0.8`
включительно направляется в Astra, значения выше `0.8` принимаются локально.
Для запроса выбираются 4–8 хронологических кадров вокруг интервала; фрагмент
изображения содержит размеченные прямоугольники назначенных сотрудника, клиента
и, при наличии карты, закреплённого за клиентом стола.

Astra подтверждает только предложенную пару и интервал. Строгий ответ состоит
из `is_service`, `staff_id`, `customer_id` и `confidence`; координаты, новые
идентификаторы и изменённые границы не принимаются. Уверенность конечного
автомата остаётся в поле `confidence`, а уверенность проверяющего модуля
хранится отдельно как `verifier_confidence`. Отклонённый кандидат отсутствует в
`events`, `service_intervals` и расчёте ожидания, но остаётся в аудите
`service_candidates`.

Экспериментальные CSV относятся к режиму без дополнительной проверки
обслуживания. Отдельная оценка каскада требует сохранённых вердиктов Astra и
отложенных видео: отрицательное решение зрительно-языковой модели способно
удалить истинное событие вместе с обеими его границами.

## Локальное подтверждение кандидатов

Опция `--service-verifier local` использует те же диапазоны
`<0.3 / 0.3–0.8 / >0.8`, но средний диапазон обрабатывается полностью локально.
На последовательности до 48 кадров вычисляются направление корпуса сотрудника,
близость запястий к клиенту и домашнему столу, наклон к цели, наличие
чашек/посуды/подноса рядом с руками и непрерывная длительность контакта.
Версионированный JSON-MLP возвращает бинарное решение; признаки и основания
решения сохраняются в `service_candidates`.

Начальный файл весов `config/service_mlp_bootstrap.json` имеет ручную
инициализацию и служит исполняемой стартовой конфигурацией. Для сравнения
качества нужен обученный файл из `train_service_mlp.py` и отложенный набор
эпизодов. Стандартный детектор COCO не содержит классов `tray`/`plate`, поэтому
эти признаки требуют пользовательской объектной модели. Полностью приватный
запуск использует `--no-astra --service-verifier local`; качество
идентификаторов и ролей в нём ограничено локальным трекером.

В галерейном прогоне `hybrid+service-local` пара `3→17` с ненаблюдаемой левой
границей отклоняется, пара `38→6` подтверждается, а `8→14` принимается по высокой
уверенности конечного автомата. В результате остаются два интервала. Строгая F1
равна `0.667`; основной источник строгой ошибки — отказ ReID объединить короткий
фрагмент траектории, а не бинарное решение проверяющего модуля. Это проверка
работоспособности начальной модели на том же клипе, а не независимая оценка.

## Текущий результат основного конвейера

| Показатель | Значение | Что означает |
|---|---:|---|
| Покрытие якорей | 30/30 | каждый размеченный человек получил предсказанный ID |
| Итоговые ID | 55 | фрагментация остаётся: число ID больше 30 реальных людей |
| Общая непрерывность | 0.855 | главный ID покрывает 85.5% ожидаемого присутствия |
| Точность ролей | 0.933 | одна из 30 ролей либо сопоставлений ошибочна |
| Строгая F1 событий | 0.667 | учитываются тип, время и участники |
| Нестрогая F1 событий | 0.889 | учитываются только тип и время |
| tIoU ожидания | 0.748 | временные интервалы ожидания совпадают на 74.8% |
| tIoU потребления | 0.746 | временные интервалы потребления совпадают на 74.6% |

Разница между строгой и нестрогой F1 показывает, что основная оставшаяся
ошибка относится к идентификаторам участников. Снижение порога объединения не
является безопасным универсальным решением: оно может объединить разных людей.
Для коротких фрагментов полезнее расширять визуальный контекст галереи или
добавлять локальные признаки внешности.

## Как расширять эталон

Для полноценной оценки нового алгоритма нужен не один клип, а набор сцен с
разной освещённостью, плотностью людей и положением столов. Рекомендуемый
порядок добавления клипа:

1. Сохранить исходное видео без изменения частоты кадров и разрешения.
2. Разметить несколько опорных кадров, включая начало, середину и конец.
3. Для каждого человека указать роль и ожидаемый интервал присутствия.
4. Разметить события с участниками и временными отметками.
5. Разметить интервалы ожидания и потребления независимо от событий.
6. Проверить разметку визуально и небольшим синтетическим тестом метрик.
7. Отделить клипы настройки порогов от отложенных клипов итоговой оценки.

При нескольких клипах метрики следует агрегировать по клипам и сопровождать
интервалами неопределённости. Подбор порогов и итоговая оценка на одних и тех же
данных завышают ожидаемое качество на новых сценах.

Актуальные результаты и ограничения одного короткого клипа описаны в [`../reports/EXPERIMENTS.md`](../reports/EXPERIMENTS.md).
