# Бизнес-метрики видеоаналитики и интеграция с POS

Этот документ описывает возможности развития FlowMetric в двух направлениях:

1. метрики, которые можно получить из видео после доработки существующего
   конвейера;
2. результаты, которые становятся доступны после объединения видеоаналитики с
   событиями POS-системы.

Документ не является описанием уже реализованного API. Текущая версия
FlowMetric выделяет вход, выход, выход сотрудника из кухни, посадку,
обслуживание, ожидание и потребление заказа. Остальные события ниже требуют
новых правил, состояний, классов объектов, обучающей разметки или POS-адаптера.

## Доступные источники сигналов

Текущий конвейер уже предоставляет основу для расширения:

- YOLO и трекер находят людей, строят траектории и оценивают длительность их
  присутствия;
- ReID объединяет фрагменты траекторий, а Astra или локальная эвристика
  назначает роли `staff` и `customer`;
- карта камеры задаёт зоны двери и кухни, а карта столов связывает посетителя с
  конкретным столом;
- конечный автомат находит посадку и интервалы взаимодействия пары
  «сотрудник–посетитель»;
- модель позы даёт положение корпуса, рук и ключевых точек;
- объектная модель распознаёт доступные в COCO чашки, миски, бокалы, бутылки и
  столовые приборы; подносы и тарелки требуют специализированных весов;
- Astra может проверять визуальную семантику короткой последовательности, но
  её действующий контракт возвращает только бинарное подтверждение общего
  обслуживания.

## Уровни готовности

В таблицах используются три уровня доработки:

| Уровень | Что требуется |
|---|---|
| Низкий | Новые правила и агрегации поверх существующих траекторий, ролей, событий и карты столов |
| Средний | Новый конечный автомат, калибровка зон, использование позы и предметов либо расширение контракта Astra |
| Высокий | Новая размеченная выборка, специализированные веса или многоклассовая модель, проверка на разных камерах |

## Метрики потока посетителей

| Метрика или событие | Определение | Доработка |
|---|---|---|
| Посетители за период | Число уникальных посетителей с событием входа | Низкая |
| Выходы за период | Число уникальных посетителей с подтверждённым выходом | Низкая |
| Текущее число посетителей | Входы минус выходы с поправкой на людей, видимых в начале и конце интервала | Низкая |
| Длительность визита | Время между входом и выходом одного идентификатора | Низкая |
| Время до посадки | `seated_at - entered_at` | Низкая |
| Уход без посадки | Вход и последующий выход без события `seated` | Низкая |
| Вход в очередь | Устойчивая остановка посетителя в откалиброванной зоне очереди | Средняя |
| Время в очереди | Время от входа в очередь до выхода из неё или посадки | Средняя |
| Уход из очереди | Выход из зоны очереди с последующим выходом из заведения без посадки | Средняя |
| Конверсия в посадку | Доля вошедших посетителей, которые сели за стол | Низкая |

Для счётчиков за период необходимо определять правило уникальности. Один
непрерывный глобальный ID считается одним визитом; повторный приход после
достаточно длинного отсутствия должен создавать новый `visit_id` даже при
уверенном ReID.

## Загрузка и оборачиваемость столов

| Метрика или событие | Определение | Доработка |
|---|---|---|
| `table_occupied` | Начало устойчивой занятости стола одним или несколькими посетителями | Низкая |
| `table_vacated` | Исчезновение всех посетителей стола после защитного временного окна | Низкая |
| Длительность занятия стола | `table_vacated - table_occupied` | Низкая |
| Коэффициент загрузки стола | Суммарное время занятости / время наблюдения доступного стола | Низкая |
| Среднее число гостей за столом | Временное среднее числа одновременно привязанных к столу посетителей | Низкая |
| Оборачиваемость | Число завершённых посадок на стол за период | Низкая |
| Простой стола | Время от готовности свободного стола до следующей посадки | Средняя |
| Время подготовки стола | Уход последней группы → окончание уборки или первая следующая посадка | Средняя |
| Пересадка | Устойчивая смена домашнего стола посетителя | Средняя |
| Группа посетителей | Люди, которые совместно вошли, двигались и заняли один стол | Средняя |

Карту столов следует калибровать отдельно для каждой камеры. Перекрывающиеся
столы, высокая плотность людей и частичные окклюзии требуют вероятностной
привязки и хранения уверенности, а не жёсткого назначения в каждом кадре.

## Скорость и качество обслуживания

| Метрика или событие | Определение | Доработка |
|---|---|---|
| Время до первого контакта | Посадка → начало первого подтверждённого обслуживания | Низкая |
| Число подходов | Количество раздельных эпизодов обслуживания одного стола | Низкая |
| Интервал между подходами | Время между окончанием одного и началом следующего эпизода | Низкая |
| Длительность контакта | Продолжительность подтверждённого эпизода обслуживания | Низкая |
| Стол без внимания | Длительность занятости без подтверждённых подходов сотрудника | Низкая |
| Нарушение SLA первого контакта | Время до первого контакта превысило настроенный норматив | Низкая |
| Нарушение SLA ожидания | Состояние `waiting` длится дольше настроенного норматива | Низкая |
| Уход без обслуживания | Посетитель сел и вышел без подтверждённого контакта | Низкая |
| Уход после долгого ожидания | Долгое ожидание без результата, после которого посетитель покинул зал | Низкая |
| Повторный контакт | Второй и последующие подходы к тому же столу | Низкая |
| Одновременная нагрузка сотрудника | Число активных столов и незавершённых запросов, связанных с сотрудником | Средняя |

Показатели по конкретному сотруднику допустимы только при достаточно надёжной
идентификации роли и личности. Их следует использовать для анализа процесса и
распределения нагрузки, а не как единственное основание для кадровых решений.

## Детализация типа обслуживания

Сейчас FlowMetric распознаёт обобщённый эпизод `service`. Сочетание траекторий,
позы, предметов и визуально-языковой модели позволяет ввести более детальные
кандидаты:

| Событие | Возможные визуальные признаки | Доработка |
|---|---|---|
| `order_taking` | Сотрудник обращён к клиенту, длительно находится у стола, руки взаимодействуют с зоной стола, подача предмета не наблюдается | Высокая |
| `food_delivery` | Поднос, тарелка или миска рядом с руками сотрудника до контакта и у стола после контакта | Средняя/высокая |
| `drink_delivery` | Чашка, бокал или бутылка переносится сотрудником к столу | Средняя |
| `table_check` | Короткий повторный разговор без передачи предметов | Высокая |
| `dish_clearing` | Посуда наблюдается на столе до контакта и у рук сотрудника после него | Средняя/высокая |
| `table_cleaning` | Сотрудник взаимодействует со свободным столом после ухода гостей | Средняя/высокая |
| `customer_call` | Поднятая рука или устойчивый жест посетителя, направленный в сторону персонала | Средняя |
| `staff_response` | Подход сотрудника после `customer_call` | Средняя |
| `eating_start` | Повторяющиеся движения рук между столом и лицом при неподвижном посетителе | Средняя/высокая |
| `drinking_start` | Поднесение распознанной чашки, бокала или бутылки к лицу | Средняя/высокая |
| `visual_payment` | Передача счёта, карты, наличных или работа с терминалом | Высокая |

Для этих событий нужна многоклассовая разметка последовательностей
«до–во время–после». Отдельный кадр обычно не позволяет надёжно отличить
подачу от уборки или принятие заказа от обычного разговора.

`visual_payment` означает только визуально похожее взаимодействие. Видео не
подтверждает успешность финансовой операции; подтверждение может дать только
POS или платёжная система.

## POS как источник бизнес-фактов

POS дополняет видео точными транзакционными событиями. Минимально полезный
контракт интеграции содержит:

```text
event_id
event_type
event_time
order_id
table_id
employee_id
shift_id
terminal_id
```

Рекомендуемые типы POS-событий:

| POS-событие | Смысл |
|---|---|
| `order_opened` | Создан заказ или открыт стол |
| `item_added` | В заказ добавлена позиция |
| `item_voided` | Позиция отменена |
| `order_sent` | Заказ отправлен на кухню или бар |
| `order_ready` | Заказ или его часть отмечены готовыми |
| `precheck_printed` | Сформирован предварительный счёт |
| `payment_started` | Начата оплата |
| `payment_completed` | Оплата успешно завершена |
| `order_closed` | Заказ закрыт |
| `order_cancelled` | Заказ отменён |
| `refund_completed` | Проведён возврат |

Суммы, состав заказа и способ оплаты следует подключать отдельным расширением:
они не обязательны для временных метрик и требуют более строгого режима
доступа к данным.

## Связывание POS и видео

Основная цепочка идентификаторов имеет вид:

```text
POS order_id
  → POS table_id
  → table_id на карте камеры
  → визуальная посадка/группа посетителей
  → эпизоды обслуживания
```

Для связывания не требуется распознавание лиц. Основой служат соответствие
номеров столов и временные окна. Результат сопоставления должен хранить:

- `video_table_id` и `pos_table_id`;
- идентификаторы заказа и визуального визита (`order_id`, `visit_id`);
- исходное и скорректированное время;
- использованное временное окно;
- метод сопоставления;
- числовую уверенность и причины неоднозначности.

Часы камеры и POS необходимо синхронизировать. Даже небольшой постоянный сдвиг
искажает короткие интервалы, поэтому адаптер должен оценивать `clock_offset`,
хранить его версию и не переписывать исходные временные метки.

Если на одном столе одновременно открыто несколько чеков либо стол в POS не
совпадает с физическим столом, связь должна оставаться неоднозначной. Нельзя
принудительно назначать заказ конкретному человеку только по близости.

## Результаты объединения видео и POS

После сопоставления доступны следующие сквозные метрики:

| Метрика | Расчёт | Что показывает |
|---|---|---|
| Время до открытия заказа | `order_opened - seated` | Скорость первого оформления |
| Время принятия заказа | `order_sent - seated` | Весь интервал от посадки до отправки |
| Время оформления после контакта | `order_sent - first_service_start` | Продолжительность клиентской части заказа |
| Время приготовления | `order_ready - order_sent` | Работа кухни или бара |
| Время готового заказа до подачи | `visual_delivery - order_ready` | Задержка выдачи готового заказа в зал |
| Полное время до подачи | `visual_delivery - seated` | Клиентское ожидание результата |
| Расхождение POS и фактической подачи | `visual_delivery - POS_delivery_mark` при наличии отметки | Качество ручных статусов POS |
| Время потребления | Начало визуального потребления → запрос счёта или оплата | Продолжительность основного этапа визита |
| Время расчёта | `payment_completed - precheck_printed` | Скорость закрытия визита |
| Время до ухода после оплаты | `table_vacated - payment_completed` | Задержка освобождения стола |
| Время уборки | `table_ready - table_vacated` | Скорость подготовки к следующей посадке |
| Полный цикл стола | Посадка одной группы → готовность стола для следующей | Фактическая оборачиваемость |
| Конверсия посетитель → заказ | Визиты со связанным заказом / все наблюдаемые визиты | Потери до покупки |
| Выручка на столо-час | Выручка связанных заказов / часы занятости столов | Эффективность использования мест |
| Средний чек на гостя | Сумма заказа / оценённый размер группы | Экономика групп разного размера |
| Нагрузка сотрудника | Одновременные столы, подходы и POS-заказы сотрудника | Распределение операционной нагрузки |

Следует различать три вида результата:

- **POS-подтверждённый факт** — например, успешная оплата;
- **визуально наблюдаемое событие** — например, физическая подача блюда;
- **вычисленная гипотеза** — например, соответствие конкретной визуальной
  посадки заказу.

В отчёте они не должны смешиваться в одно поле без указания источника и
уверенности.

## Контроль расхождений и узких мест

Совместная система может формировать диагностические сигналы:

- посетитель давно сидит, но заказ не открыт;
- заказ отправлен, но время приготовления превысило норматив;
- заказ готов, но визуальная подача долго не наблюдается;
- физическая подача наблюдается, но подходящий заказ или статус готовности не
  найден;
- заказ закрыт, но стол продолжает быть занят;
- гости ушли, а заказ остаётся открытым;
- стол освободился, но долго не был убран;
- POS указывает занятый стол, на котором посетители не наблюдаются;
- у одной визуальной посадки найдено несколько конкурирующих заказов;
- сотрудник или номер стола в POS расходится с наиболее вероятным визуальным
  взаимодействием.

Такие записи являются сигналами для проверки, а не автоматическим доказательством
ошибки или нарушения. Причиной могут быть неверная карта столов, рассинхронизация
часов, окклюзия, перенос заказа, разделение счёта или ручная работа с POS.

## Рекомендуемый формат сквозного результата

Для каждого визита удобно формировать агрегат:

```json
{
  "visit_id": "visit-...",
  "video_table_id": 4,
  "pos_table_id": "T-04",
  "order_ids": ["order-..."],
  "customer_ids": ["12", "18"],
  "entered_at": null,
  "seated_at": "...",
  "first_service_at": "...",
  "order_opened_at": "...",
  "order_sent_at": "...",
  "order_ready_at": "...",
  "delivered_at": "...",
  "payment_completed_at": "...",
  "table_vacated_at": "...",
  "table_ready_at": "...",
  "match_confidence": 0.91,
  "evidence": {
    "order_opened_at": "pos",
    "delivered_at": "video",
    "payment_completed_at": "pos"
  }
}
```

`null` означает ненаблюдаемую границу, а не нулевую длительность. Для всех
вычисленных интервалов полезно сохранять признаки `left_censored` и
`right_censored`, как это уже сделано для обслуживания.

## Предлагаемый порядок внедрения

1. Добавить поверх существующих результатов занятость столов, длительность
   визита, время до первого контакта, число подходов и SLA ожидания.
2. Ввести `visit_id` и устойчивое состояние стола: занят, освобождён, ожидает
   уборки, готов.
3. Реализовать POS-адаптер для пяти базовых событий: `order_opened`,
   `order_sent`, `order_ready`, `precheck_printed`, `payment_completed`.
4. Настроить соответствие POS-столов карте камеры и синхронизацию времени.
5. Сформировать сквозной агрегат визита и отчёт о неоднозначных связях.
6. Разметить реальные эпизоды подачи и уборки, обучить многоклассовый
   классификатор и только после проверки качества добавлять принятие заказа,
   сигнал клиента и визуальную оплату.

## Ограничения и проверка качества

- Все пороги необходимо валидировать на отложенных видео с разных камер, смен,
  уровней освещения и плотностей посетителей.
- Для каждого нового события нужны precision, recall и F1; для длительных
  состояний — временной IoU и ошибка границ интервала.
- Для POS-связей дополнительно нужна точность сопоставления
  `visit_id ↔ order_id` и доля неоднозначных или несопоставленных заказов.
- Метрики времени следует считать отдельно для наблюдаемых и цензурированных
  интервалов.
- Отсутствие визуального события не доказывает отсутствие действия: его могла
  скрыть окклюзия или граница кадра.
- Персональные и финансовые данные следует минимизировать. Для большинства
  операционных метрик достаточно псевдонимизированных ID, номера стола,
  временных меток и типа события; изображения и состав чека не должны
  передаваться в POS-адаптер без отдельной необходимости.
