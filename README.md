# FlowMetric

FlowMetric анализирует видео зала кафе со статичной камеры. Система находит людей,
сохраняет их идентификаторы между кадрами, определяет роли «сотрудник» и
«посетитель», а затем выделяет события входа, выхода, посадки и обслуживания.

Проект состоит из четырёх основных этапов:

1. YOLO11s с входным размером 1280 пикселей находит людей, а BoT-SORT связывает
   обнаружения между соседними кадрами. Профиль повышенной полноты сохраняет
   также дальние и низкоуверенные обнаружения.
2. Модель GPT-6 Astra получает изображения с сеткой миниатюр («контактные
   листы»), составленные из пронумерованных фрагментов траекторий (в коде —
   `tracklet`). Она связывает только уже существующие локальные идентификаторы,
   определяет роли либо возвращает явный отказ от решения (в данных —
   `abstain`). Исходные полные кадры в этот запрос не входят.
3. Локальные фрагменты объединяются по нескольким взвешенным подтверждениям.
   Склейка с низкой уверенностью отклоняется, а пространственно разные люди,
   одновременно видимые в кадре, объединяться не могут.
4. Конечный автомат событий и отдельный автомат состояний клиента определяют
   вход, выход, выход из кухни, посадку, обслуживание, ожидание (`waiting`) и
   потребление заказа (поля `waiting` и `consuming`).

Дополнительный режим `--service-verifier astra` проверяет неоднозначные
кандидаты обслуживания. Кандидаты с уверенностью правил ниже `0.3` отклоняются
локально, значения от `0.3` до `0.8` включительно направляются в Astra, а
значения выше `0.8` принимаются локально. Astra получает 4–8 фрагментов кадров
с уже назначенными идентификаторами сотрудника и клиента. При наличии карты
столов отмечается также стол. Ответ содержит только `is_service`, пару
идентификаторов и поле уверенности `confidence`; модель не создаёт боксы,
идентификаторы или новые границы интервала.

Режим `--service-verifier local` использует ту же маршрутизацию без отправки
кадров во внешний API. Для неоднозначного эпизода локально запускаются модель
позы и детектор предметов. По положению корпуса и рук, наклону, посуде и
длительности контакта небольшой многослойный перцептрон (`MLP`) принимает
решение. Он также не может менять идентификаторы или границы интервала.

Каждое решение повторной идентификации (`ReID`) записывается как объединение
(`merge`), отклонение (`reject`) или отказ от решения (`abstain`) вместе с
уверенностью, числом подтверждений и причиной. По умолчанию объединение требует
минимум двух подтверждающих фрагментов и взвешенную уверенность не ниже `0.55`.
Структура непересекающихся множеств (`union-find`) учитывает жёсткие запреты на
объединение. Слой ретроспективной памяти сохраняет исходные свидетельства и
перестраивает гипотезы в порядке их уверенности: сильное позднее свидетельство
может отменить слабое раннее объединение. Такие изменения сохраняются в
`identity_sync.revision_log`. Координаты всегда поступают из локального детектора.

Результат запуска — размеченное видео, `tracks.json`, `events.json` и, если
передан эталон, `benchmark_report.json`. Обслуживание хранится как точечные
события `service_start`/`service_end` и как интервалы `service_intervals`.
Интервалы дополнительно показывают, наблюдалась ли каждая граница. Раздел
`service_candidates` содержит аудит принятых и отклонённых кандидатов.

Возможные бизнес-метрики после развития видеоаналитики, а также результаты
объединения событий камеры и POS описаны в
[`BUSINESS_METRICS.md`](BUSINESS_METRICS.md).

## Термины

| Термин в коде | Русское объяснение |
|---|---|
| detection | обнаружение человека на одном кадре |
| bounding box, box | ограничивающий прямоугольник вокруг человека |
| track | траектория человека на последовательности кадров |
| tracklet | короткий локальный фрагмент траектории |
| контактный лист | изображение с сеткой подписанных миниатюр кадров или фрагментов кадров |
| ReID | повторная идентификация: определение, какие фрагменты принадлежат одному человеку |
| confidence | числовая уверенность алгоритма в результате |
| precision / recall | точность / полнота; в формулах обозначаются P и R |
| false positive / false negative | ложноположительный / ложноотрицательный результат |
| FSM | конечный автомат, то есть набор состояний и правил перехода между ними |
| left/right-censored | левая/правая граница интервала находится за пределами наблюдаемого видео |
| сквозная оценка (`end-to-end`) | оценка всей цепочки, включая пропущенных людей |
| mapped | оценка только успешно сопоставленных с эталоном людей; это имя используется в полях отчёта |

## Структура

```text
flowmetric/
  pipeline.py             управление этапами и интерфейс командной строки
  config.py               PipelineConfig и настройки этапов
  device.py               проверенный выбор CPU, Apple MPS или NVIDIA CUDA
  domain/models.py        общие структуры Track, ServiceInterval и Decision
  tracking/local.py       YOLO и локальное сопровождение людей
  identity/gallery.py     галереи фрагментов траекторий и схема ReID
  identity/memory.py      ретроспективная память и аудит пересмотров ReID
  identity/sync.py        взвешенное объединение, запреты и отказ от решения
  service/fsm.py          конечный автомат кандидатов обслуживания
  service/astra.py        Astra-проверка неоднозначных кандидатов
  service/local.py        признаки позы/предметов и локальный MLP
  customer/states.py      независимые состояния ожидания и потребления
  media/video.py          общие операции с кадрами, фрагментами и траекториями
  infrastructure/astra.py Astra API и версионированные кэши
  events.py               сборка событий и состояний
  output.py               tracks.json и рендер видео
track.py                  совместимая точка входа командной строки
astra.py, events.py       совместимые фасады импорта
train_service_mlp.py      обучение JSON-MLP по размеченным признакам
scene.py                  загрузка и проверка калибровки камеры/столов
metrics.py                ID, роли, события P/R/F1 и tIoU состояний
tables.py                 построение статичной карты столов
config/                   зоны камеры, карта столов, настройки трекера
benchmark/                эталон для тестового клипа
experiments/              сетка детекторов, трекеров, ReID и зрительно-языковых моделей
reports/                  CSV с результатами и отчёт по экспериментам
tests/                    модульные тесты метрик, событий, кэша и конфигурации сцены
data/                     входное видео и результаты прогонов
```

Для программного запуска используется `flowmetric.config.PipelineConfig` с
отдельными `TrackingConfig`, `IdentityConfig` и `ServiceConfig`. Команда
`python track.py` и импорты из корневых модулей предоставляют совместимый
интерфейс; также доступен запуск `python -m flowmetric`.

Зависимости направлены от внешних слоёв к внутренним. Общие структуры из
`domain/` не импортируют модели, API или командную строку. Проверяющие модули
обслуживания зависят от общих структур и видео-утилит, но не от сборщика
событий. Поэтому новый способ проверки можно добавить без изменения форматов
`tracks.json` и `events.json`.

## Установка

Для основного конвейера нужны Python, `pip` и системные библиотеки, необходимые
OpenCV и PyTorch. Полная экспериментальная сетка имеет отдельные зависимости и
может требовать Python 3.11 из-за ограничений версий BoxMOT. Начинающему
разработчику рекомендуется сначала запустить основной конвейер и тесты.

```bash
# macOS / Linux
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Нужен только для режимов Astra. Для полностью локального запуска пропустите.
echo "VSELLM_API_KEY=..." > .env      # либо OPENAI_API_KEY
```

Веса Ultralytics загружаются при первом обращении, если соответствующего файла
нет в `weights/`. Это сетевой запрос, который выполняется только для получения
модели; режим `--no-astra` не отправляет анализируемое видео во внешний API.

Проверить установку без обработки видео:

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python track.py --help
```

## Запуск

Самый простой локальный запуск не требует API-ключа:

```bash
python track.py \
  --source data/hf_20260519_173215_0e502bf6-374c-4039-ab2e-fded1fdf5558.mp4 \
  --out data/output/local/tracked.mp4 \
  --no-astra
```

После завершения рядом с видео появятся `tracks.json`, `events.json` и, если
указан `--gt`, `benchmark_report.json`. Каталог `data/output/` исключён из Git:
результаты локальных запусков не попадут в коммит автоматически.

```bash
# Гибридный режим; результаты попадут в data/output/
python track.py

# Подключить заранее построенную карту столов
python track.py --tables config/tables.json

# Только локальный трекинг, без API
python track.py --no-astra

# Проверять неоднозначные события обслуживания через Astra
python track.py --service-verifier astra

# Локальный трекинг с отдельной Astra-проверкой обслуживания
python track.py --no-astra --service-verifier astra

# Полностью локальный контур: кадры не отправляются во внешний API
python track.py --no-astra --service-verifier local --tables config/tables.json

# Гибридный ReID и локальное подтверждение обслуживания
python track.py --service-verifier local --tables config/tables.json

# Пересчитать метрики для существующих tracks.json/events.json
python metrics.py
```

### Основные параметры командной строки

| Параметр | Назначение |
|---|---|
| `--source` | исходное видео |
| `--out` | путь к размеченному видео; JSON-файлы записываются в тот же каталог |
| `--model`, `--imgsz`, `--conf` | модель детектора, размер входа и порог уверенности |
| `--tracker` | YAML-конфигурация алгоритма сопровождения |
| `--device` | устройство вычислений: `auto`, `cpu`, `mps`, `cuda`, `cuda:N` или номер CUDA-карты |
| `--camera` | зоны двери, кухни и края кадра |
| `--tables` | необязательная карта столов |
| `--gt` | эталонная разметка для автоматической оценки |
| `--no-astra` | отключить Astra ReID; отдельная Astra-проверка обслуживания включается только явным флагом |
| `--astra-cache` | кэш решений повторной идентификации |
| `--reid-merge-confidence` | минимальная взвешенная уверенность объединения |
| `--reid-min-support` | минимальное число подтверждающих фрагментов |
| `--service-verifier` | `off`, `astra` или полностью локальный режим `local` |

Полный список и значения по умолчанию выводит `python track.py --help`.

Интерактивный воспроизводимый сценарий с явной конфигурацией локальной и
гибридной веток находится в [`notebook.ipynb`](notebook.ipynb). Ноутбук также
показывает сводку метрик, аудит решений и визуальную проверку результата.

### CPU, Apple MPS и NVIDIA CUDA

По умолчанию `--device auto` выбирает CUDA, затем Apple MPS, а при отсутствии
доступного ускорителя — CPU. Выбор применяется к основному детектору и трекеру;
локальная проверка обслуживания использует то же устройство. Параметр
`--local-service-device` нужен только для отдельного переопределения, например
когда детектор должен работать на MPS, а модель позы — на CPU.

```bash
# Любая машина: принудительно использовать CPU
python track.py --no-astra --device cpu

# Mac с Apple Silicon и PyTorch с поддержкой Metal
python track.py --no-astra --device mps

# Первая или конкретная NVIDIA-видеокарта
python track.py --no-astra --device cuda
python track.py --no-astra --device cuda:1

# Детектор на MPS, локальная проверка обслуживания на CPU
python track.py --no-astra --device mps \
  --service-verifier local --local-service-device cpu
```

Явный запрос недоступного устройства завершает запуск до обработки видео. Это
предотвращает незаметный переход на CPU и ошибочные сравнения скорости. Для
CUDA нужна CUDA-сборка PyTorch; для MPS — Apple Silicon, поддерживаемая macOS и
сборка PyTorch с MPS. Команда `auto` остаётся переносимым вариантом для общих
сценариев и ноутбука.

## Поток данных

```text
видео
  → локальные обнаружения и короткие траектории
  → необязательная Astra ReID и взвешенное объединение идентификаторов
  → итоговые траектории tracks.json
  → конечный автомат обслуживания и состояния клиента
  → события и интервалы events.json
  → сравнение с ground_truth.json
  → benchmark_report.json
```

На каждом этапе сохраняются только данные, разрешённые его контрактом. Astra
ReID группирует локальные идентификаторы, но не меняет координаты. Проверяющий
модуль обслуживания принимает или отклоняет предложенный интервал, но не меняет
его участников и временные границы. Такой контракт упрощает поиск источника
ошибки: геометрия относится к детектору, идентичность — к этапу ReID, а
семантика обслуживания — к конечному автомату и проверяющему модулю.

## Форматы результатов

### `tracks.json`

Файл содержит параметры видео и словарь итоговых траекторий. Ключ словаря —
строковый итоговый идентификатор человека.

```json
{
  "mode": "hybrid+service-local",
  "fps": 24.0,
  "width": 1920,
  "height": 1080,
  "n_frames": 361,
  "device": "mps",
  "service_device": "mps",
  "tracks": {
    "7": {
      "role": "customer",
      "tids": [4, 19],
      "frames": [0],
      "boxes": [[100.0, 200.0, 160.0, 360.0]],
      "conf": [0.91],
      "identity_status": "merged",
      "identity_confidence": 0.87
    }
  },
  "identity_sync": {}
}
```

Массивы `frames`, `boxes` и `conf` должны быть выровнены по индексам. Поле
`tids` перечисляет локальные идентификаторы, вошедшие в итоговую личность.
Раздел `identity_sync` хранит подробный аудит решений объединения.

### `events.json`

В `events` находятся точечные события, в `states` — временные состояния, а в
`service_intervals` — эпизоды обслуживания с наблюдаемыми и ненаблюдаемыми
границами.

```json
{
  "events": [
    {"t": 9.25, "type": "service_start", "staff": "8", "customer": "14"}
  ],
  "states": [
    {"type": "waiting", "person": "14", "start": 2.0, "end": 9.25,
     "confidence": 0.85, "evidence": "verified_delivery"}
  ],
  "service_intervals": [
    {"staff": "8", "customer": "14", "start": 9.25, "end": 12.792,
     "left_censored": false, "right_censored": false, "confidence": 0.855}
  ]
}
```

Не следует восстанавливать интервалы только из точечных событий: интервал с
границей за пределами клипа может намеренно не иметь `service_start` или
`service_end`.

### `benchmark_report.json`

Отчёт содержит сопоставление эталонных и предсказанных идентификаторов,
покрытие якорей, непрерывность траекторий, роли, строгую и нестрогую оценку
событий и временной IoU состояний. Определения приведены в
[`benchmark/README.md`](benchmark/README.md).

Калибровки в `config/camera.json` и `config/tables.json` содержат разрешение исходного кадра. `scene.py` проверяет разрешение, геометрию зон и боксы столов до детекции и API-вызовов. Карта от другого имени файла допускается с предупреждением, но только если положение камеры действительно не менялось.

Карту столов можно перестроить отдельно:

```bash
python tables.py --video data/example.mp4 --device auto
```

### Кэш Astra

По умолчанию ответ сохраняется в `data/output/astra_reid.json`. Это
версионированный кэш с манифестом: в нём проверяются хеш и размер видео,
частота кадров, разрешение, число кадров, выбранные кадры и пакеты, модель,
уровень рассуждения (`effort`), версии галереи, запроса и схемы, система
координат и полнота покрытия. Кэш хранит связи локальных фрагментов траекторий,
уверенность, число подтверждений и явные отказы от решения.

- Совпадающий кэш используется повторно.
- Устаревший, повреждённый или относящийся к другому запуску кэш отклоняется; при наличии API-ключа он атомарно заменяется новым.
- Основной конвейер принимает только версионированный формат с манифестом. Кэш без манифеста отклоняется; без API-ключа используйте `--no-astra` либо сформируйте совместимый кэш с ключом.

Экспериментальный раннер читает сохранённые Astra-ответы из `data/experiments/` для воспроизводимости сетки.

### Идентичности и состояния клиента

Основной ReID-запрос содержит только страницы с фрагментами изображений
локальных траекторий. Каждый фрагмент подписан `tracklet=<id>, frame=<frame>`;
полный исходный кадр и координаты в Astra не передаются. Модель обязана
распределить каждый идентификатор ровно один раз: в одну группу личности либо в
`abstained_tracklet_ids`. Параметры `--reid-merge-confidence` и
`--reid-min-support` управляют локальным решением об объединении. Полный аудит
находится в `tracks.json → identity_sync`; итоговые траектории содержат
`identity_status` и `identity_confidence`.

Ожидание (поле `waiting`) и потребление заказа (поле `consuming`) рассчитываются как
два независимых состояния клиента. Ожидание начинается после посадки или
начальной занятости стола и завершается по подтверждённой доставке либо
наблюдаемой активности клиента. Потребление определяется отдельно: по
устойчивой занятости стола на границе клипа или по микродвижению верхней части
тела при неподвижных ногах. `events.json → customer_state_audit` хранит
использованные признаки и уверенность.

Проверяющий модуль обслуживания использует отдельный кэш
`data/output/astra_service_verification.json`. Его манифест привязан к видео,
траекториям, кандидатам, выбранным кадрам, таблице, модели, версии запроса,
схеме ответа и порогам маршрутизации. Ответ каждого запроса Astra содержит
ровно четыре поля:

```json
{"is_service": true, "staff_id": 7, "customer_id": 12, "confidence": 0.91}
```

Несовпадающие идентификаторы, дополнительные поля, нечисловая уверенность и
кэш с другим манифестом отклоняются. При недостатке четырёх совместных кадров
кандидат сохраняет решение конечного автомата с пометкой
`insufficient_visual_evidence`; ошибка API не трактуется как отрицательный
ответ.

### Локальная проверка по позе и предметам

Локальный режим выбирает кадры с частотой 4 кадра/с, но не более 48 кадров,
строит одну область изображения для всей последовательности и запускает
`yolo11n-pose.pt` вместе с объектной моделью. Стандартный набор классов COCO в
`yolo11n.pt` распознаёт чашки, миски, бокалы, бутылки и столовые приборы. Для
подносов (`tray`) и тарелок (`plate`) нужны специализированные веса, переданные
через `--local-object-model`. Веса модели позы могут скачиваться Ultralytics при
первом запуске; анализируемое видео при этом не отправляется наружу.

`config/service_mlp_bootstrap.json` — консервативная начальная модель, а не
калиброванный промышленный классификатор. В
`events.json → service_candidates[].decision.details` сохраняются все 12
признаков, покрытие позы, найденные предметы, длительность контакта и
вероятность MLP. При недостаточном покрытии позы кандидат сохраняется с
`insufficient_pose_evidence`: отсутствие обнаружения не считается
доказательством отсутствия обслуживания.

Обучение собственного чекпойнта выполняется по JSON/JSONL-строкам вида `{"label": true, "features": {...}}`:

```bash
python train_service_mlp.py \
  --features data/service_features.jsonl \
  --out config/service_mlp.json

python track.py --no-astra --service-verifier local \
  --local-service-model config/service_mlp.json \
  --tables config/tables.json
```

## Проверки

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m compileall -q flowmetric tests
git diff --check
```

Набор тестов не обращается к внешнему API. Клиент Astra, загрузчик кадров и
модели в тестах заменяются управляемыми заглушками. Полный прогон основного
конвейера значительно тяжелее модульных тестов и запускается отдельно.

### Как вносить изменения

1. Определите слой, которому принадлежит изменение. Структуры данных находятся
   в `flowmetric/domain`, сопровождение — в `tracking`, повторная идентификация —
   в `identity`, обслуживание — в `service`, состояния клиента — в `customer`.
2. Не добавляйте зависимость внутреннего слоя от `pipeline.py` или корневых
   совместимых фасадов. Внутри пакета используйте импорты `flowmetric.*`.
3. Сохраните текущие JSON-контракты либо явно добавьте версию формата и тест
   миграции. Экспериментальные кэши должны проверять происхождение данных.
4. Для исправления ошибки сначала добавьте небольшой воспроизводящий тест.
5. Запустите модульные тесты, компиляцию и `git diff --check`.
6. Для изменения алгоритма повторите эталонный прогон и сравните не только F1,
   но также покрытие людей, непрерывность идентификаторов и временной IoU
   состояний.

Корневые файлы `track.py`, `events.py`, `astra.py`, `identity_gallery.py`,
`service_verifier.py` и `local_service_verifier.py` являются фасадами
совместимости. Новую реализацию следует добавлять в пакет `flowmetric/`, а не в
эти файлы.

## Типичные проблемы

- **Видео не найдено.** Передайте явный `--source`; автоматический выбор первого
  файла удобен только для локальной разработки.
- **Калибровка не соответствует разрешению.** Используйте конфигурацию камеры и
  столов, подготовленную для того же разрешения и положения камеры.
- **Astra-кэш отклонён.** Видео, параметры, модель или версия запроса отличаются
  от манифеста. Нужен API-ключ для формирования нового кэша либо `--no-astra`.
- **Нет API-ключа.** Используйте `--no-astra`; режим
  `--service-verifier astra` также требует ключ или подходящий отдельный кэш.
- **Локальная проверка не находит позу.** Проверьте веса, устройство
  `--local-service-device` и сохранённое поле `insufficient_pose_evidence`.
- **Появилось слишком много идентификаторов.** Изучите
  `tracks.json → identity_sync`: причиной может быть отказ Astra, недостаточное
  число подтверждений или жёсткий пространственно-временной запрет.

## Результаты на эталонном клипе

Основная непрерывность (`continuity`) и точность ролей считаются сквозным
образом по всей цепочке обработки: пропущенный эталонный человек получает ноль. Значение
для сопоставленного подмножества (`mapped`) оценивает только людей, которых
удалось связать с якорями, и всегда читается вместе с покрытием. Первые две
строки — контрольные прогоны основной команды с профилем повышенной полноты;
гибридный галерейный режим использует локальную проверку обслуживания. Другие
строки относятся к воспроизводимой экспериментальной сетке с сохранёнными
ответами зрительно-языковой модели.

| Конфигурация | Строгая F1 (точность/полнота) | ID | Покрытие якорей | Непрерывность общая / сопоставленная | Роли общие / сопоставленные |
|---|---:|---:|---:|---:|---:|
| BoT-SORT с повышенной полнотой, полностью локально | 0.500 (0.571/0.444) | 74 | **30/30** | 0.617 / 0.617 | 0.933 / 0.933 |
| BoT-SORT + галерея Astra + локальная проверка обслуживания | 0.667 (0.667/0.667) | 55 | **30/30** | **0.855 / 0.855** | **0.933 / 0.933** |
| YOLO11s 1280 + BoxMOT 12 BoT-SORT + Astra 1 fps | 0.824 (0.875/0.778) | 34.0 | 26/30 | 0.804 / 0.928 | 0.867 / 1.000 |
| Лучший результат сетки: BoostTrack BoxMOT 25 + Astra | **0.941 (1.000/0.889)** | 42.3 | 28/30 | 0.852 / 0.912 | 0.933 / 1.000 |
| OccluBoost BoxMOT 25 + Astra | 0.800 (1.000/0.667) | 37.0 | 26/30 | 0.802 / 0.925 | 0.867 / 1.000 |

Галерейный прогон покрывает `30/30` человек; временной IoU ожидания равен
`0.748`, потребления — `0.746`. Одно короткое наблюдение сотрудника остаётся в
состоянии отказа от решения, поэтому строгая F1 с проверкой участников равна
`0.667`, а нестрогая F1 только по типу и времени — `0.889`. Такой режим отдаёт
приоритет точности объединения идентификаторов: недостаточные визуальные
доказательства не превращаются в принудительную склейку. Результаты относятся
к одному 15-секундному проверочному клипу; пороги требуют оценки на отложенных
видео. Трекеры BoxMOT 25 доступны в экспериментальной сетке.

В галерейном режиме `hybrid+service-local` начальный MLP отклоняет один интервал
с ненаблюдаемой левой границей и сохраняет два подтверждённых обслуживания.
Полностью локальный режим даёт F1 `0.500`; основное ограничение — фрагментация
идентификаторов и определение ролей без Astra ReID.

Строгая F1 отвечает на вопрос «правильно ли определены событие, время и оба
участника». Нестрогая F1 отвечает только на вопрос «произошло ли событие этого
типа примерно в это время». Большой разрыв между ними обычно указывает на
ошибку идентичности, а не на ошибку временной границы события.

Подробная методика и таблицы сравнения 222 конфигураций приведены в
[`reports/EXPERIMENTS.md`](reports/EXPERIMENTS.md). Для воспроизведения полной
сетки нужны зависимости из `requirements-experiments.txt`.
